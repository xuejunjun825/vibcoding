PRD · DevOps 研发管理平台（需求全流程 MVP）

本 PRD 由需求方与产品在会话中逐条确认后整理，覆盖 11 组已确认细节（角色、三类需求、人天口径、业务方视图、双维度隔离、自定义审批流、二级企业、岗位工作台、范围与非目标、验收要点、技术栈）。凡文中「假设」字样处均为待确认项，未确认前按默认值执行。

1. 背景与目标

1.1 业务背景

供应链平台项目体量大，已划分 7 个业务域，由多家软件厂商团队承接需求研发与迭代；集团下还有二级管理企业，其业务人员也需要直接向平台反馈需求。当前缺少统一的需求入口与流转工具：需求散落在邮件/群里、审批靠线下签字、多厂商之间数据不隔离、业务方看不到进度、人天投入算不清、管理层没有可信的效能数据。

用户要求仿制嘉为蓝鲸（canway.net）的 DevOps 研发工具体系，先做其中「DevOps 研发效能平台」的需求全流程部分；蓝鲸矩阵中的 CPack / CCode / CAgent / CTest / CWiki / CTeam / CMeas / CCI / CFlow 九个平台本期不做，作为后续迭代。

1.2 目标（本期必须达成）

  1. 一条需求能走完全链路：二级企业业务人员或业务部门提报 → 本企业/直属主管审批 → 集团产品经理评审入池 → 拆解为产品需求与研发需求 → 厂商研发承接并填人天 → 测试通过 → 发布审批 → 关闭，每一步状态、权限、留痕都正确。
  2. 审批可自定义：需求提报、评审入池、需求版本、需求发布四类单据都支持按流程定义走审批，流程可在界面上配置（会签/或签/条件分支/抄送），改流程不影响在途单据。
  3. 数据按「域 × 厂商」隔离：厂商用户在任何入口（列表、搜索、导出、附件、看板）都看不到其他厂商的数据；甲方 PMO/管理层跨域全量。
  4. 业务方看得见进度与成本：业务部门与二级企业业务人员能看到自己需求的进度、预计交付、预估/已投入/偏差人天。
  5. 各岗位有工作台：8 类角色登录后看到与自身职责匹配的待办、快捷动作与数据看板，看板数字与明细页一致。
  6. 数据可自助分析：支持拖拽维度/度量即时生成交叉表与图表，保存为可复用报表；任意报表与导出都受数据权限过滤，导出行数与页面一致，且导出带水印。
  7. 交付后半段闭环：研发交付可落到「任务 → 迭代 → 测试 → 缺陷 → 发布上线单 → 发布结果」，发布前有准入校验（需求全测过、无未关闭 P0/P1 缺陷等），缺陷可追溯到需求与版本。
  8. 工时与产能可度量：成员填报工时，实际人天自动回写需求；按「厂商 × 人 × 周」看负载与超载，避免排期拍脑袋。
  9. 平台可集成：提供开放 API 与出站 Webhook（签名 + 重试），关键指标口径收敛到「指标字典」并可一键导出周报/月报。
  10. 测试管理闭环：测试用例库（用例 + 步骤 + 用例版本）可维护，测试计划按版本组织，执行结果回写需求/版本；自动化用例接收外部 CI 上报的执行结果（本期不自建执行器），失败可一键转缺陷。
  11. 知识沉淀：项目级 Wiki 支持空间/页面树、Markdown 编辑、版本对比与全文检索，需求/缺陷/版本可关联 Wiki 页。
  12. 计划与流动可视化：甘特图按版本/迭代/需求展示时间轴并可拖拽调整（落库），价值流看板按阶段展示在制品、停留时长、流动效率与瓶颈。
  13. 多租户可部署：支持「同库行级 / 独立 schema / 独立库」三种隔离形态并按租户切换，新建租户自动初始化库结构，切换后数据完全隔离且功能一致。

1.3 本期不做（见 §10 范围与非目标）

九个外围平台中的 CPack / CCode / CAgent / CMeas / CCI（制品库、代码托管、AI 助手、效能洞察独立产品、流水线执行器）；移动端 H5；AI 能力；表单自定义引擎；金额成本折算；多级会签；自建 CI/CD 流水线执行器（只接收外部上报结果）；SSO/LDAP。

2. 用户与角色

平台共 9 类用户（业务角色 8 类 + 平台管理员）。一人可挂多角色，权限取并集；审批人由流程定义动态指定，不写死角色。

业务部门 甲方业务线 提报业务需求、跟踪本部门需求进度与人天 本部门提报及相关 业务需求提报（直属主管/部门负责人）

补充规则：

  • 域负责人是「项目」角色的一个维度：7 个域各配负责人，域内可见本域全部厂商；厂商用户即使被授权进入某域，也只能看到与自己相关的行（见 §7）。
  • 厂商负责人是研发/测试中的管理岗位：可指派本厂商人员、看本厂商全部需求与交付率，不能跨厂商。
  • 管理层 vs PMO：管理层默认只读（除被登记为终审节点），PMO 有排期/分派/流程配置等操作权。

3. 业务流程与状态机

3.1 端到端主流程

二级企业业务人员/业务部门
        │ 提报（业务需求）
        ▼
[审批：本企业负责人 → 集团产品经理]（可配）
        ▼
   待评审 ──产品经理评审──► 已入池（需求池）
        │                      │
        │                      ├─ 产品经理拆解出 产品需求（挂父）
        │                      │        └─ 再拆解出 研发需求（挂父）
        │                      ├─ 纳入版本计划（Release + 里程碑）
        │                      └─ 分派厂商（跨厂商转派留痕）
        ▼                      ▼
    驳回 → 回到提报人        厂商研发承接 → 开发中 → 待测试 → 测试通过 → 已合入
                                                        │
                                                        ▼
                                            发布申请 → [发布审批] → 已发布 → 完成

3.2 三类需求状态机（按类型分化，非法流转一律拒绝）

类型 编号前缀 状态流转
业务需求 BUS 提报 → 审批中 → 待评审 → 已入池 →（关闭 / 驳回回提报人）
产品需求 PDR 待分析 → 已排期 → 开发中 → 已交付 → 验收关闭
研发需求 RD 待开发 → 开发中 → 待测试 → 测试通过 → 已合入 → 完成
  • 三类需求都是父子三层：业务需求 → 产品需求 → 研发需求；子需求必须挂父，一个父可挂多个子，可跨 Release。
  • 父需求详情页展示子需求清单、完成率（按计数或加权）、人天汇总、交付状态。
  • 每次状态流转写审计日志（操作人、时间、来源、备注），不允许任何接口绕过状态机直接改状态。

3.3 审批与状态机联动

单据 触发 审批通过 审批驳回
需求提报 提交提报 进入「待评审」 回「已提报」，可改后重提
评审入池 产品经理发起评审 进「已入池」 退「待评审」
需求版本 版本发布申请 版本「已发布」，级联推进关联需求 退「已排期」，需重新编辑
需求发布 研发完成发布申请 单据落「完成」，进入交付统计 退「待测试/开发中」，按流程节点回退

3.4 跨厂商协作

  • 需求转派：域负责人把需求从厂商 A 转给厂商 B，写转派记录（谁、何时、原因），B 厂商才可见。
  • 共享池：域负责人可把需求公开到共享池，供多家厂商认领；认领后归属唯一的 assignee_vendor。
  • 跨域关联：业务需求有主域 1 个 + 关联域 N 个，关联域的域负责人可见该需求（只读摘要）。

3.5 交付后半段的对象关系

研发需求(RD) ──拆──► 任务 Task ──属于──► 迭代 Sprint（挂在 Release 下）
     │                    │
     │                    └── 工时 worklog ──汇总──► 实际人天（回写 RD）
     ├── 测试记录（通过/不通过） ──不通过──► 缺陷 Defect（BUG-xxxx，可重开）
     └── 发布上线单 DeployOrder ──准入校验(5 项)──► 审批 ──► 发布结果(成功/失败/回滚)
  • 追溯链：需求 → 任务 → MR 链接 → 测试记录 → 缺陷 → 发布单/版本，任一侧可反查（§4.16、§9 AC-26）。
  • 口径：需求「是否可发布」由准入校验决定，不靠人工口头确认；缺陷未关闭 P0/P1 直接阻断发布。

4. 功能需求

4.1 组织、厂商、业务域与账号

  • 组织树：集团（一级）→ 二级管理企业 → 部门 → 人员；支持按企业批量建号、指定企业负责人。
  • 厂商管理：名称、编码、联系人、状态；厂商下再挂团队人员。
  • 业务域管理：7 个域可配置（编码、名称、负责人、启用状态），后续可增删。
  • 用户：归属组织 + 所属厂商（厂商人员）+ 被授权域集合；登录、启停、重置密码。
  • 角色与权限：角色可配功能权限；数据范围由 §7 的规则引擎统一裁决（不是每个页面各写一套）。

4.2 需求提报

  • 表单字段：类型（业务/产品/研发）、标题、描述、所属业务域、优先级、期望交付时间、附件、提报单位（自动带出组织）、关联域（业务需求可选多个）。
  • 二级企业业务人员：提报时先做相似需求提示（按标题/描述关键词，取最像 5 条），可「我也需要」挂到已有需求上，也可继续独立提报。
  • 提报后进入审批流（默认两级：本企业负责人 → 集团产品经理；集团内部为直属主管 → 产品经理），审批中可撤回。
  • 驳回后回提报人，可修改重提；重提生成新的审批实例，保留历史。

4.3 需求池

  • 按类型（业务/产品/研发）分 Tab；筛选条件：父需求、版本、负责人、优先级、状态、业务域、厂商、提报企业、时间范围。
  • 两种视图：父需求聚合视图（默认，显示子需求完成率与汇总人天）、平铺视图（逐条需求）。
  • 业务方（业务部门/二级企业）可见的池：业务需求按 §7 规则过滤；二级企业用户只读浏览已入池的业务需求摘要（标题、摘要、所属域、状态、预计版本），不含人天/成本/内部备注、不含研发细节。
  • 列表支持导出 CSV（同样受数据权限过滤）。

4.4 需求评审与入池

  • 产品经理对「待评审」需求发起评审：选择评审流程 → 提交 → 进入审批；通过后进池。
  • 评审记录：评审意见、驳回原因、附带的关联需求。
  • 入池后可被版本计划引用、被拆解。

4.5 需求拆解

  • 业务需求页面「拆解」→ 新建产品需求（父=业务需求）；产品需求「拆解」→ 新建研发需求（父=产品需求）。
  • 拆解时继承业务域、可覆盖优先级/交付期望；校验父子类型合法、禁止环。
  • 父需求上可见子清单与完成率；子需求状态变化实时回写父的聚合值。

4.6 版本计划

  • Release：编码、名称、所属域、计划发布日、状态（规划中/已锁定/已发布/已取消）、里程碑列表。
  • 版本可挂三类需求（业务需求按产品需求聚合展示），支持拖拽调整（二期可做，MVP 用列表勾选）。
  • 版本发布需走发布审批；通过后版本状态置「已发布」，关联需求状态按规则推进。
  • 版本详情页展示：需求清单、完成情况、人天预估/实际、风险需求（延期）。

4.7 研发交付

  • 厂商研发从需求池认领/被分派研发需求 → 状态「开发中」→ 填 MR 链接（手工填写，本期不对接代码平台）。
  • 人天填报：研发需求填预估人天、实际人天（0.5 天精度）+ 负责人；产品需求与业务需求由子需求自动汇总（只读，不可手填）。
  • 测试：测试人员执行测试 → 通过/不通过 + 缺陷记录；通过后进「已合入」。
  • 发布申请：研发/厂商负责人提交发布 → 发布审批（可配运维会签）→ 通过后单据「完成」。

4.8 自定义审批流

引擎：自研轻量审批引擎（不引入 Flowable/Camunda——Boot 4.0.9 + JDK 25 的第三方兼容性有风险，且场景是固定单据的线性/条件流）。

  • 流程定义：按单据类型（需求提报/评审入池/需求版本/需求发布）建流程，可叠加「需求类型（业务/产品/研发）× 业务域」绑定不同流程；每类单据可设一个默认流程。
  • 节点：开始 → 审批节点（会签 / 或签）／条件分支节点（按需求类型、业务域、优先级、预估人天路由）／抄送节点 → 结束。
  • 审批人来源：指定人、角色（产品经理/域负责人/PMO）、发起人直属主管、厂商负责人；支持节点级多人配置。
  • 加签 / 减签：审批人处理时可加签——前加签（新增审批人先于本人处理）、后加签（本人处理完再交给新增审批人，可多选人）；节点负责人或管理员可减签（从待处理审批人中移除，需填原因并通知被减签人）。加签/减签均写流转历史；会签节点加签后必须新成员全部处理完毕才能流转到下一节点；已处理的审批任务不可加签。
  • 版本化：流程发布即固化版本；修改流程生成新版本，在途实例继续按启动时版本执行，改流程不得导致卡死或跳步；已发布版本不可编辑。
  • 配置器：表单式节点列表配置（不做 BPMN 拖拽画布，二期再评估）。
  • 审批中心：我的待办 / 已办 / 我发起的；详情展示流转记录（谁、何时、意见）、被审单据摘要（可跳转）、附件；操作：同意、驳回、加签、减签、转办、撤回、催办；超时站内提醒（邮件/企微/钉钉留扩展）。
  • 数据模型：wf_definition（单据类型+需求类型+域+版本+定义 JSON+启用）、wf_instance、wf_task、wf_history。
  • 权限：流程定义仅 PMO/管理员可编辑；审批人查看被审单据时受同一套数据权限约束（跨域/跨厂商审批只给摘要字段，不提供明细下载）。
  • 表单：本期表单字段固定；表单自定义引擎二期。

4.9 岗位工作台

4.13 系统管理

4.14 缺陷管理

  • 缺陷单：编号 BUG-0001；字段=标题、描述与复现步骤、严重级（P0 致命/P1 严重/P2 一般/P3 轻微）、优先级、关联研发需求、关联版本、发现人、处理人、所属域与厂商（隔离字段）、附件。
  • 来源：测试执行「不通过」自动生成（带测试记录链接）；也支持手工提缺陷（测试/运维/研发）。
  • 状态机：新建 → 处理中 → 待验证 → 关闭；待验证可驳回回「处理中」（重开）；关闭后可重开（记重开次数）；每次流转写 audit_log 并回写需求时间线。
  • 归属：处理人默认取 assignee_vendor 的研发负责人，可指派给该厂商内成员。
  • 列表与看板：按域/厂商/版本/严重级/状态/处理人筛选；关键指标=未关闭 P0/P1 数、缺陷密度（缺陷数/需求数）、重开率、平均修复时长。
  • 隔离与可见：走 §7 统一过滤；业务方可看到自己提报需求衍生的缺陷摘要（仅状态与预计修复时间），看不到研发细节。

4.15 任务与迭代

  • 任务（Task）：研发需求下可拆任务（标题、负责人、预估小时、截止日、状态=待办/进行中/完成/阻塞、排序）；任务变更写审计；任务完成率回写研发需求进度、工时汇总计入实际人天（§4.17）。
  • 迭代（Sprint）：挂在某 Release 下的时间盒（名称、起止日、目标、容量人天、状态=规划中/进行中/已关闭）；研发需求与任务可挂迭代。
  • 看板：迭代看板（状态列可拖动、按人泳道）、个人任务清单（工作台复用）；燃尽按任务数或人天（可切换）。
  • 关闭规则：关闭迭代时未完成任务必须迁移到下一迭代或退回待办，未迁移禁止关闭。
  • 权限：产品/域负责人建迭代与分配；研发更新自己任务状态；PMO 可查看全部。

4.16 发布上线单与准入校验

  • 发布单：关联 Release、需求清单（自动带出）、目标环境（测试/准生产/生产）、计划窗口、制品版本号（手工填，可空）、上线步骤、回滚方案、影响范围、负责人。
  • 准入校验（提交时自动执行，逐项展示 PASS/FAIL）：① 关联需求全部测试通过；② 无未关闭 P0/P1 缺陷；③ 研发需求 MR 链接已填；④ 人天（预估/实际）已填；⑤ 需求级审批已通过。任一 FAIL 禁止提交；PMO 可「强制放行」但必须填原因，放行写审计并通知域负责人。
  • 审批：可配运维会签/多级审批（走 §4.8 流程引擎，单据类型=需求发布）。
  • 执行记录：实际开始/结束时间、结果（成功/失败/回滚）、耗时、执行人、备注；失败可关联网页缺陷并重新发起。
  • 统计：发布日历（按环境/版本）、发布成功率、平均发布耗时、失败原因分布。

4.17 工时填报与产能

  • 工时登记：按人、按天、按需求/任务登记，精度 0.5h，可写备注；支持周视图批量填报；月度可锁定（锁定后不可改，需管理员解锁并留痕）。
  • 回写口径：研发需求实际人天 = 工时合计 ÷ 8；与 §4.7 手填人天二选一——默认以填报为准，手填仅 PMO/管理员修正并记修正记录（口径写入指标字典，避免两套数）。
  • 产能视图：按「厂商 × 人 × 周」展示可用人天（默认 5）、已排需求/任务人天、负载率与超载预警（>100% 标红）；排期与分派时提示超载。
  • 报表：工时分布（人/域/厂商/版本）、人天偏差（预估 vs 实际）、人员饱和度。

4.18 指标字典与报告

  • 指标字典：每条指标含编码、名称、主题（需求/交付/质量/效率/成本）、公式、数据源表、口径说明、负责人、版本、生效日期；看板与报表上的数字可点击查看定义并下钻到明细（AC-29）。
  • 补齐指标：需求前置时间（提报→交付）、按时完成率、需求吞吐量、在制品 WIP、需求丢弃率、缺陷密度、缺陷重开率、发布成功率、平均发布耗时、工时利用率、预估人天偏差率、厂商准时交付率。
  • 报告：周报/月报/季报模板（XLSX，复用 §4.11 导出与水印）：核心指标 + 环比 + Top 问题（延期需求、未关闭 P0/P1、超载人员/厂商）；一键生成并下载；本期手动触发，定时订阅二期。
  • 一致性：报告与看板必须复用同一聚合接口（§4.10），禁止两套 SQL 各算一遍；指标字典变更需记录版本。

4.19 开放 API 与集成

  • 开放 API：api_client（名称、AppKey、密钥哈希、scope、IP 白名单、限流 QPS、状态）；首批接口=需求创建/查询/状态变更、审批结果查询、版本与发布单查询；全部调用写审计，错误码固定。
  • 出站 Webhook：订阅事件=需求状态变更、审批结果、版本发布、缺陷状态变更、发布单结果；JSON payload + HMAC-SHA256 签名 + 时间戳（防重放）+ 失败指数退避重试（最多 5 次）+ 投递日志（可查/可重发）。
  • 字段级脱敏：field_visibility 规则（字段 × 角色/数据范围 → 可见/掩码/不可见），成本人天、厂商评分、内部备注默认仅管理层/PMO 可见；页面、接口、导出、报表四个出口复用同一套字段过滤（AC-31）。

4.20 测试用例库与测试执行

  • 用例树：项目/域 → 模块（3 层内）→ 用例；支持拖拽移动、批量导入（CSV/XLSX，模板校验）、批量导出（带水印）、复制/禁用。
  • 用例字段：编号 TC-xxxx、标题、模块、关联需求（可选）、用例类型（功能/接口/性能/兼容）、优先级 P0–P3、前置条件、步骤（序号/操作/预期结果）、标签、是否自动化。
  • 用例版本：每次保存生成版本（v1、v2…），执行记录绑定用例版本；改完用例不影响历史执行的可追溯性（这是用例库与“测试记录”最大的区别）。
  • 用例评审：可作为第五类审批单据（可开可关，MVP 默认关闭），通过后才可被测试计划引用（若开启）。
  • 测试计划：挂在 Release/版本下，选择用例集合 + 执行人 + 时间窗；执行状态=未执行/通过/失败/阻塞/跳过；汇总为计划通过率与覆盖率。
  • 执行与缺陷：执行记录含结果、实际结果说明、附件（截图/日志）；失败可一键生成缺陷（自动带用例、版本、需求、执行记录）；研发需求「测试通过」的前置条件=计划内用例全部执行且无失败（可配置门禁）。
  • 自动化执行（不自建执行器）：用例标记 automated + 脚本标识；外部 CI（Jenkins / GitLab CI 等）通过开放 API（§4.19）上报「用例 + 结果 + 耗时 + 日志链接 + run_id」→ 生成执行记录（source=AUTO）；上报按 run_id + case_id 幂等；手工与自动结果并存，以最新为准并保留趋势。
  • 统计：用例通过率、执行覆盖率、缺陷检出率、自动化占比、失败率趋势、Top 不稳定用例（连续失败次数）。

4.23 价值流看板（CFlow）

  • 阶段可配：默认 提报 → 评审 → 排期 → 开发 → 测试 → 发布 → 交付；每阶段由「状态/事件」映射（如「评审」= 待评审→已入池）；阶段可启停、排序、按需求类型启用不同阶段集。
  • 指标：各阶段 WIP、平均停留时长、P90、每周流入/流出、流动效率（活跃时间 / 总前置时间）、瓶颈阶段、交付周期分布（直方图）。
  • 下钻：点阶段 → 需求列表（受权限过滤）；点需求 → 阶段停留时间线（来自 audit_log 状态流转时间）。
  • 口径：阶段进入/退出时间取状态流转审计时间；跳过的阶段标灰且不参与平均；指标编码进 metric_definition，与 §4.10/§4.18 同源，禁止另算一套。
  • 视角：按域/厂商/需求类型筛选；厂商只看自己承接（§7）。

4.24 多租户与隔离部署

  • 租户模型：tenant（编码、名称、隔离形态、状态、数据源键）；一个租户=一个集团客户，租户内再分组织/厂商/业务域；平台管理员管理租户，业务用户属唯一租户。
  • 三种隔离形态（按租户配置，可迁移）：
    • ROW 同库行级（默认）：所有业务表带 tenant_id，拦截器强制注入 + 查询强制校验。
    • SCHEMA 独立 schema：共用实例、按租户切 schema。
    • DATABASE 独立库：按租户注册独立 DataSource（多数据源 + 路由）。
  • 数据源路由：AbstractRoutingDataSource + 请求上下文（JWT 内 tenantId）；异步任务/导出/Webhook/MQ 消费必须显式传递租户上下文，禁止依赖 ThreadLocal 隐式丢失；无租户上下文时直接拒绝，不落默认库。
  • 开通与迁移：新建租户自动创建 schema/库并执行 Flyway 初始化 + 预置角色/字典；提供 ROW → SCHEMA/DATABASE 迁移工具（导出、导入、行数与关键表校验和对比、可回滚）。
  • 边界：无任何跨租户明细查询接口（平台级只出聚合数字）；导出、附件、开放 API、报表同样按租户路由；租户创建/切换/迁移/删除全部写审计。
  • 一致性：三种形态共用同一套业务代码与 Flyway 脚本，仅在数据源层分流；验收时在 SCHEMA 与 DATABASE 各跑一遍核心链路（AC-35）。

7. 数据隔离与可见性规则

隔离维度：业务域（domain）× 厂商（vendor）。隔离强度：MVP 同库行级过滤（统一拦截器注入），表结构预留切独立 schema/库。

判定规则（按优先级短路）：

  1. 管理层 / PMO / 平台管理员（系统类）：全量可见（管理层默认只读，除非被配置为审批节点）。
  2. 甲方业务角色（业务部门/产品/项目/域负责人/甲方测试/甲方运维）：
    • PMO/域负责人：所辖域全量（本域所有厂商）；
    • 产品：所负责域/产品线全量；
    • 业务部门：本部门提报及相关需求；
    • 二级企业业务人员：自己提报的需求 + 全集团已入池业务需求的摘要（只读）；
    • 二级企业负责人：本企业全部提报。
  3. 厂商角色（研发/测试/厂商负责人）：行可见当且仅当 row.domain_id ∈ user.authorized_domains 且（row.owner_vendor_id = user.vendor_id 或 row.assignee_vendor_id = user.vendor_id 或该行被共享给其厂商）。
  4. 审批场景：审批人处理审批时能看到被审单据的摘要字段；若其数据权限不含该单据明细，则只展示摘要，不提供附件/明细下载。
  5. 统一生效面：需求、缺陷、任务、工时、发布单、审批、看板聚合、报表、统计接口、附件下载必须走同一套行级过滤（MyBatis 拦截器 + 统一上下文），禁止只在列表接口做过滤；开放 API 与 Webhook 载荷同样只含调用方可见范围的数据。
  6. 租户边界（最外层）：所有业务数据先按租户路由——ROW 形态在 SQL 层强制 tenant_id，SCHEMA/DATABASE 形态由数据源路由切换；租户上下文缺失或与请求不一致一律拒绝（400/403），不允许“落到默认库”。平台管理员看租户列表与聚合统计，但跨租户明细查询接口不提供。
  7. 字段级脱敏（与行级隔离正交）：field_visibility 按角色/数据范围配置字段为「可见/掩码/隐藏」，默认规则——成本人天与偏差、厂商评分、内部备注仅管理层/PMO 可见；二级企业业务人员看业务需求池时不含人天与内部字段；页面、接口、导出、报表四个出口复用同一套字段过滤，不允许某一出口漏配。

9. 用户故事与验收标准

AC 编号在本需求内从 AC-1 起。

US-1（P0）三类需求与三层拆解

  • AC-1：可分别创建业务/产品/研发需求，编号前缀分别为 BUS/PDR/RD；子需求必须挂父需求且父子类型合法（业务→产品→研发），非法组合被拒绝并给出原因。
  • AC-2：三类需求按各自状态机流转；非法流转（如研发需求跳过测试直接完成）被接口拒绝；每次流转写审计日志。
  • AC-3：三级父子汇总正确：子需求人天/完成率实时回写到父，父需求不可手工填写人天；跨 Release 挂载不破坏汇总。

US-2（P0）双维度数据隔离

  • AC-4：厂商 A 用户在任何入口（列表、详情、搜索、导出、附件、看板）均看不到厂商 B 承接的需求，越权直连 URL 返回 403。
  • AC-5：域授权生效：未被授权域的厂商用户看不到该域需求；被撤销授权后立即失效。
  • AC-6：甲方 PMO/管理层可见全量；跨厂商转派后新厂商立即可见、原厂商不可见，转派记录可查。
  • AC-7：二级企业业务人员可浏览全集团已入池业务需求摘要，但看不到人天/成本明细、研发细节与其他企业需求明细。

US-3（P0）自定义审批流

  • AC-8：四类单据均可配置流程并启用；不同「需求类型 × 域」可绑定不同流程；默认流程生效。
  • AC-9：会签（全员通过才过）、或签（任一通过即过）、条件分支（按需求类型/域/优先级路由）、抄送节点均正确执行。
  • AC-10：流程版本化：发布 v2 后，新建单据走 v2，在途单据仍按 v1 走完，不卡死、不跳步、不重复。

  • AC-12：审批结果驱动状态机：提报通过进待评审、驳回回提报人；评审通过入池、驳回退待评审；版本发布通过级联推进、驳回退已排期。

  • AC-13：需求池支持类型 Tab 与多维筛选，父需求聚合视图与平铺视图数据一致；筛选与导出遵守数据权限。

  • AC-23 导出与水印：交叉表与明细均可导出 XLSX（默认）与 CSV；XLSX 必带水印（页眉/页脚含报表名、导出人、时间、筛选条件 + 正文平铺半透明水印 + 文档属性），CSV 首行含水印元信息并在界面提示；导出文件行数与页面一致且仅含权限内数据，导出动作写审计日志；超过数据量阈值时导出走异步任务并给出下载入口。

US-9（P0）缺陷闭环

  • AC-24：测试执行「不通过」可一键生成缺陷（自动带需求/版本/测试记录）；缺陷按 新建→处理中→待验证→关闭 流转，待验证可驳回回处理中并计重开次数；关闭后可重开；P0–P3 严重级可筛选；缺陷列表与看板（未关闭 P0/P1、缺陷密度、重开率、平均修复时长）数字与明细一致；缺陷增删改查遵守 §7 双维度隔离，厂商 B 看不到厂商 A 的缺陷。

US-10（P0）发布上线单与准入校验

  • AC-25：发布单必须关联 Release 并自动带出需求清单；提交时自动执行 5 项准入校验（需求全测过 / 无未关闭 P0/P1 缺陷 / MR 已填 / 人天已填 / 审批已过）并逐项展示 PASS/FAIL；任一 FAIL 时提交被拒绝且给出具体失败项；PMO 强制放行必须填原因，放行写审计并通知域负责人；发布单审批通过后可记录执行结果（成功/失败/回滚）与实际耗时。

US-11（P0）需求追溯矩阵

  • AC-26：任一类需求的详情页可看到完整追溯链：需求 → 任务 → MR 链接 → 测试记录 → 缺陷 → 发布单/版本时间线；矩阵页按需求维度展示各环节是否齐备，可筛选「缺 MR / 缺测试 / 有未关闭缺陷 / 未发布」等缺口；追溯数据不跨权限边界（厂商只看自己承接需求的链路）。

US-12（P0）任务与迭代

  • AC-27：研发需求可拆任务（负责人/预估小时/截止日），任务状态更新后需求进度与工时汇总相应回写；迭代挂在 Release 下，可把需求与任务加入迭代；迭代看板拖动改状态后刷新一致；关闭迭代时存在未迁移任务则拒绝关闭并提示。

US-13（P0）工时与产能

  • AC-28：成员可按周批量填报工时（0.5h 精度），月度锁定后不可改；研发需求实际人天由工时汇总（÷8）回写且与手填值不会同时生效（口径冲突有明确提示）；产能视图按「厂商 × 人 × 周」给出可用/已排/负载率，超载（>100%）标红；PMO 修正工时需填写原因并留痕。

US-14（P0）指标字典与报告

  • AC-29：每个看板/报表数字可点击查看指标定义（编码/公式/口径/负责人）；周报可由页面一键生成 XLSX 并下载，含核心指标、环比与 Top 问题清单，导出文件带水印；报告与看板对同一筛选条件结果一致（同一聚合接口）。

US-15（P1）邮件与 Webhook

  • AC-30：配置 SMTP 后，审批待办/超时、发布结果、缺陷指派可发送邮件（未配置时不影响站内通知）；Webhook 订阅按事件推送，载荷带 HMAC 签名与时间戳；接收方返回非 2xx 时按退避重试最多 5 次，投递日志可查、可手动重发；签名错误或时间戳过期的事件被视为重放被拒并记录。

US-16（P0）开放 API 与字段级脱敏

  • AC-31：开放 API 需 AppKey/Secret 签名 + 时间戳，未授权 scope 或 IP 不在白名单返回 401/403 并记审计；接口返回的数据范围与账号权限一致；被配置为「隐藏/掩码」的字段在页面、接口、导出、报表四个出口均不出现原文（导出与 API 返回同时验证）；字段级规则改动后无需重启即生效。

US-17（P0）测试用例库与测试执行

  • AC-32 用例库与执行闭环：可建模块树（≤3 层）并在其下维护用例（步骤、优先级、类型）；修改用例后生成新版本，历史执行记录仍显示当时的用例版本；测试计划可挂版本并纳入用例，执行结果（通过/失败/阻塞/跳过）落库并汇总为计划通过率与覆盖率；执行失败可一键生成缺陷且自动带用例、版本、需求、执行记录；研发需求「测试通过」在启用门禁时被拒绝，除非计划内用例全部执行且无失败。
  • AC-33 自动化结果上报：外部 CI 用开放 API 上报执行结果，同一 run_id + case_id 重复上报幂等（不产生重复记录）；上报结果与手工执行在同一用例下按时间合并，最新结果决定计划状态；上报数据经字段校验（未知用例/版本直接拒绝并返回错误码）；自动化上报失败不影响手工执行与其他接口。

US-18（P0）Wiki 知识库

  • AC-34 Wiki：可建空间与最多 4 层页面树；Markdown 编辑保存后生成页面版本，可对比任意两个版本并回滚；正文全文检索命中受空间可见范围过滤（厂商 A 搜不到厂商 B 的「仅本厂商」空间内容）；被需求/缺陷/版本引用的 Wiki 页在两侧都能互相看到链接；删除进回收站，30 天内可恢复；页面中的脚本/事件属性在执行前被过滤。

US-19（P0）甘特图与价值流

  • AC-35 甘特：版本/迭代/需求可在甘特上按日/周/月查看计划条与实际条；拖动改期后刷新页面日期已落库、审计有记录；超出父版本窗口时提示且需确认（拒绝情形明确提示）；300 条以内首屏 ≤1.5s，超出按层级折叠。
  • AC-36 价值流：可配置阶段与状态映射；看板展示各阶段 WIP、平均停留时长、P90、流动效率与瓶颈阶段；任选一条需求可看到阶段停留时间线，且与 audit_log 状态流转时间一致；点阶段下钻的需求列表遵守数据权限（厂商只看自己承接）；看板数字与 §4.10 看板同筛选条件下一致。

US-20（P0）多租户与隔离部署

  • AC-37 多租户：平台管理员可建租户并选择 ROW / SCHEMA / DATABASE 三种形态；新建租户自动初始化库结构与预置数据，登录后数据不与其他租户交叉；请求缺少或不匹配租户上下文时被拒绝（不落默认库）；把租户从 ROW 迁移到 SCHEMA 后数据行数与关键表校验和一致、可回滚；在 SCHEMA 与 DATABASE 各跑一遍「提报→审批→需求池→版本→交付→看板」核心链路均通过。

11. 反面目标（技术通过但会被退货的情形）

  1. 审批流配了但走不动：配置界面能存，但发起时报错、或改流程后老单据卡死。
  2. 隔离只在列表做了：列表看不到，但导出 Excel、附件直链、看板数字漏出别家数据。
  3. 看板与明细对不上：工作台说 12 个待评审，点进去 8 个。
  4. 状态机被绕过：通过接口直接改状态字段、或前端隐藏按钮后端不校验。
  5. 三级汇总算不拢：父需求人天与子需求之和不等，或产品需求被手工填数。
  6. 权限矩阵只测了管理员账号：厂商账号和二级企业账号一登就发现越权或看不到该看的。
  7. 工时与实际人天两套数：报表里实际人天是手填的、工时明细加起来又是另一个数，两边都“对”。
  8. 字段脱敏只在页面做：页面上人天显示为“***”，但导出 Excel / 调 API / 看报表时原文都在。
  9. 准入校验形同虚设：5 项校验能显示，但绕过前端直接调接口就能提交发布单；或强制放行没有原因、也没有审计。
  10. 用例与执行两张皮：用例改了 3 版，历史执行记录却显示的是最新内容，测试结论无法追责。
  11. 自动化上报是手填的：没有幂等与验签，重复上报产生重复执行记录，通过率被刷高。
  12. 甘特拖了不落库：界面上条动了，刷新回原位；或拖出父版本窗口也照收。
  13. 多租户只是加了个字段：报表/导出/异步任务有一处没带租户上下文，数据串到别的租户库里。

14. 工程约束

  • 运行时底座：复用 r1 交付的 api-gateway（8080）+ Nacos（8848/8849）；新增 req-service（8082：组织/用户/需求/版本/审批引擎）与 deliver-service（8083：交付/人天/测试/发布/看板聚合/工作台 API）。
  • 技术栈：Java 25 + Spring Boot 4.0.9 + Spring Cloud 2025.1.4 + SCA 2025.1.0.0；MySQL 9.6 + Flyway；MyBatis-Plus 或 Spring Data JPA（二选一，技术方案定）；前端 Vue 3 + Element Plus + Vite + ECharts。
  • 不引入：Gradle、Docker、Python 交付物、Flowable/Camunda。
  • 认证：JWT（登录签发，网关校验，服务内解析用户上下文）；权限与数据范围统一在服务层拦截器实现。
  • 接口：REST + 统一响应体 {code,message,data}；OpenAPI 文档随服务暴露；错误码表在技术方案中定义。
  • 自助报表：前端拖拽用 Element Plus 组件 + 自研投放区（行/列/值/筛选），交叉表渲染用表格组件、图表用 ECharts；后端提供统一「多维查询 API」（数据集/维度/度量/筛选/排序/分页 → 聚合结果），报表定义与权限过滤在服务端完成，不在前端拼 SQL。
  • 多租户：Spring AbstractRoutingDataSource + 租户上下文（JWT → 拦截器 → 调用链显式传递）；ROW 形态用 MyBatis 拦截器强制 tenant_id；SCHEMA/DATABASE 形态在数据源层切换；异步任务/导出/Webhook 消费显式携带 tenantId。
  • 测试管理：用例库（模块树 + 版本快照）与执行记录分表；自动化结果只做「接收 + 归一 + 合并」，不自建执行器。
