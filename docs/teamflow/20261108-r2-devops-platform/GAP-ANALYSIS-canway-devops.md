# 对标嘉为蓝鲸 DevOps 解决方案的 PRD 差距评估

- 对标材料：《2026-嘉为蓝鲸DevOps解决方案介绍.pdf》（72 页，含解决方案总览、CTeam/CCode/CCI/CPack/CTest/CMeas/CFlow 产品能力、中行与人保案例）
- 评估对象：`docs/teamflow/20261108-r2-devops-platform/PRD.md`（455 行，15 章）
- 评估日期：2026-11-08
- 结论：**主干对齐**（需求全流程 + 审批 + 版本 + 交付 + 度量闭环在 PDF 中都有对应能力域）；**缺口集中在“交付过程的后半段”与“平台化能力”**——缺陷闭环、发布单/准入、追溯矩阵、任务与迭代、工时与产能、指标字典与报告、通知渠道、开放 API。本期建议补 8 项，其余进二期 roadmap。

## 2. 建议本期补充（P0，按价值/成本排序）

### P0-1 缺陷（Bug）闭环
- 缺口：当前只有「测试不通过 + 缺陷记录」，没有缺陷实体、状态机与指标；交付质量看板因此算不准。
- PDF：CTeam「缺陷管理」、「关联缺陷」；CMeas「缺陷等级分布/重开率/缺陷密度」。
- 建议：`defect` 表（编号 BUG-0001、关联需求/版本/测试记录、严重级 P0–P3、发现人/处理人、状态 新建→处理中→待验证→关闭/重开、原因分类）；缺陷列表与看板；测试不通过自动建缺陷；发布准入校验依赖它。
- 成本：M。验收：缺陷可创建/流转/关闭重开；版本详情显示未关闭缺陷数；AC 新增 1 条。

### P0-2 发布单升级为「上线单」+ 准入校验
- 缺口：§4.7 只有「发布申请 → 审批」，缺发布内容清单、目标环境、计划窗口、回滚方案、执行结果，导致「发布成功率/发布日历」无数据来源。
- PDF：CCI「发布上线/回滚」、CD 多环境（测试/准生产/生产）+ 蓝绿/灰度；CTeam「发布审批」。
- 建议：发布单（关联 Release + 需求清单 + 制品版本号手填 + 目标环境 + 窗口 + 回滚方案 + 执行结果 成功/失败/回滚 + 耗时）；提交时自动准入校验：需求全部测试通过、无未关闭 P0/P1 缺陷、人天已填、前置审批已过；不满足则禁止提交，PMO 可强制放行并记录原因。
- 成本：M。验收：不满足条件的发布单提交被拒且提示缺哪项；放行留痕；发布结果可统计。

### P0-3 需求追溯矩阵（需求 → 任务/MR → 测试 → 发布）
- 缺口：PDF 强调「Commit 带工作项编号、MR 关联需求、构建结果回流、全链路可追溯」；我方只有手工 MR 链接字符串，无法回答「这条研发需求交付完了吗」。
- 建议（不接代码平台版本）：需求详情时间线（提报→审批→拆解→分派→MR 链接→测试记录→缺陷→发布单）；矩阵页行=需求、列=阶段（有/无），可筛「缺 MR」「缺测试」「未发布」；数据全部来自本平台手工字段，后续对接 webhook 可自动填充。
- 成本：M。验收：任一 RD-xxx 能一屏看到全链路；矩阵可导出（带水印）。

### P0-4 任务（Task）与迭代（Sprint）
- 缺口：PDF CTeam 核心是「需求→任务→迭代看板」，我方只有需求与 Release，研发无法做日粒度排期与看板拉动。
- 建议：研发需求下挂任务（标题/负责人/预估小时/状态 待办/进行中/完成/阻塞/截止日）；迭代=Release 下的时间盒（起止日、目标、容量）；任务看板（按人/按状态）；任务完成率回写研发需求进度。
- 成本：M。验收：一个迭代内可建任务、拖动状态、看板实时；需求进度由任务完成率驱动（与 AC-3 汇总口径兼容）。

### P0-5 工时填报与产能/负载视图
- 缺口：PDF 有「工时登记/工时统计/资源利用率/成员饱和度」；我方只有人天字段，无法回答「谁这周满了、哪个厂商产能不足」。
- 建议：`worklog`（用户/日期/需求或任务/工时 0.5h 精度/备注）→ 汇总实际人天；产能视图按 厂商×人×周：可用人天、已排人天、负载率、超载预警；排期时提示超载。
- 成本：M。验收：填报后实际人天自动更新（手填与填报二选一，需先定口径）；负载视图数字可核对。

### P0-6 指标字典 + 周报/月报导出
- 缺口：看板指标散在各处、口径靠文档；PDF 有「指标字典/报告管理/日报周报月报自动发送」。
- 建议：产品内「指标字典」页（指标名、公式、数据源、口径说明、负责人、版本）；报告模板（周报/月报 XLSX，复用 §4.11 导出与水印）；本期先做「一键生成 + 下载」，定时发送放二期。
- 成本：S/M。验收：每个看板数字可点开看定义；生成的周报含核心指标与环比。

### P0-7 通知渠道：邮件 + 出站 Webhook
- 缺口：PDF 有邮件/企微/钉钉/飞书与 Webhook；我方仅站内，审批超时与发布提醒出不了平台。
- 建议：SMTP 邮件通道（审批待办/超时/发布结果）；通用出站 webhook（固定 JSON payload + 签名 + 失败重试 + 投递日志），企微/钉钉适配器二期。
- 成本：S/M。验收：配置后审批待办能收到邮件；webhook 可用本地 mock 收到事件且重试可见。

### P0-8 平台开放 API 与字段级脱敏
- 缺口：PDF 强调 Open API 与「对接已有账号体系/ITSM/通知系统」；我方无对外接口，且「成本人天不可见」靠视图隔离而非字段级规则。
- 建议：对外 Open API（需求创建/查询、状态变更回调、审批结果）带 AppKey 鉴权与限流、写审计；字段级可见性规则表（字段 × 角色/数据范围），成本字段、厂商评分默认仅管理层/PMO 可见，接口与导出同一套规则。
- 成本：M。验收：API 可创建需求并在平台可见；越权字段在接口返回中被过滤而非前端隐藏。

## 3. 二期（P1）建议登记进 roadmap，暂不实现

1. 测试用例库 + 测试计划 + 覆盖率口径（CTest）。
2. Wiki/文档库与需求双向关联（CTeam 知识沉淀）。
3. 需求变更单：锁定版本内的变更影响分析（人天/里程碑/关联需求 diff）。
4. 风险登记（版本/域维度）与应对跟踪。
5. 甘特图、基线对比（两个 Release 差异）。
6. CFlow 价值流：阶段可配置、WIP 限制、漏斗与瓶颈分析。
7. 报表订阅推送（定时邮件/企微）、阈值告警。
8. 外部数据源接入（数仓/第三方平台）与仪表板模板市场。
9. SSO / LDAP / OAuth2 统一登录。
10. 移动端 H5（审批、进度）。
11. 与 CCode/CCI/CPack/CTest 类外部平台对接：MR/提交/构建/制品/测试结果 webhook 回传，自动填充 P0-3 矩阵。
12. AI 辅助（需求润色/摘要、相似需求语义化、智能问答）——PDF CAgent 能力，需单独评估成本。
13. 多租户独立库、IP 白名单、国密/等保加固、登录失败锁定与会话策略。

## 4. 明确不做（维持现行非目标）

- 自研代码托管、CI 流水线引擎、制品仓库、自动化测试平台（对应 CCode/CCI/CPack/CTest 全量能力）。
- 外部 BI 工具集成（Superset/Tableau/帆软）。
- 编译加速、代码扫描规则引擎等腾讯内部重资产能力。

## 5. 我方已超出 PDF 的能力（差异化，建议写进方案说明）

PDF 是通用产品介绍，未展开以下定制点，而我们已明确：

1. 「业务域 × 厂商」双维度行级隔离 + 统一过滤面（PDF 只在案例里讲多方协作）。
2. 二级管理企业业务人员提报与全集团需求池只读浏览。
3. 三类需求（BUS/PDR/RD）三层父子 + 差异化状态机 + 类型化权限。
4. 审批流加签/减签、流程版本化、在途实例按启动版本执行。
5. 报表默认私有 + 导出强制水印（含 CSV 元信息）。
6. 人天三级汇总口径（研发→产品→业务，父需求只读）。
