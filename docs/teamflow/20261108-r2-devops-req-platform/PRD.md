# PRD · DevOps 研发管理平台（需求全流程 · 本轮 M1–M5）

> 本文件在上一轮同需求 PRD（`docs/teamflow/20261108-r2-devops-platform/PRD.md`，因交付范围由 M1–M3 扩大而取消）基础上重写。其已确认的产品决策、`UI-STYLE.md` 视觉规范继续有效；产品全量蓝图（M1–M9）不变，**本轮只交付并验收 M1–M5**。AC 编号在本夹内从 AC-1 起独立编号，与上一轮编号的对照见 §9.1。

## 1. 背景与目标

### 1.1 业务背景

供应链平台已划分 **7 个业务域**，由**多家软件厂商团队**承接需求研发与迭代；集团下另有**二级管理企业**，其业务人员也要直接向平台反馈需求。当前需求散落在邮件与群聊、审批靠线下签字、多厂商之间数据不隔离、业务方看不到进度、人天与质量算不清、测试与缺陷两张皮。

用户要求**仿制嘉为蓝鲸（canway.net）的 DevOps 研发工具体系**，把「提报 → 审批 → 需求池 → 版本计划 → 研发交付 → 测试 → 缺陷 → 发布」串成一条可追溯、可隔离、可度量的链路。

### 1.2 本轮目标（M1–M5，必须达成）

1. **一条需求能走完全链路**：二级企业/业务部门提报 → 审批 → 产品经理评审入池 → 拆解为产品需求与研发需求 → 厂商承接填人天 → 测试计划执行 → 缺陷闭环 → 发布单准入 → 发布审批 → 完成，每一步状态、权限、留痕正确。
2. **隔离是硬的**：厂商用户在任何入口（列表、详情、搜索、导出、附件、看板、追溯矩阵、缺陷、用例）都看不到其他厂商的数据；甲方 PMO/管理层跨域全量；漏一处即不通过。
3. **审批可自定义**：需求提报、评审入池、需求版本、需求发布四类单据可配流程（会签/或签/条件分支/抄送），支持前/后加签与减签；改流程不影响在途单据。
4. **发布前有硬门禁**：发布单提交自动执行 5 项准入校验（需求全测过 / 无未关闭 P0/P1 / MR 已填 / 人天已填 / 审批已过），FAIL 即拒；PMO 强制放行必须留原因并审计。
5. **质量闭环可追责**：BUG 单可重开并计次；用例**版本化**且执行记录绑定当时版本；失败一键转缺陷并自动带出用例/版本/需求/执行记录。
6. **自动化只接收、不自建执行器**：外部 CI 经开放 API 上报执行结果，`run_id + case_id` 幂等，未知用例/版本拒收，通过率不被刷高。
7. **门禁不可绕**：研发需求「测试通过」在启用门禁时，只能由计划执行结果放行，接口与界面同一判定。
8. **数字同源**：缺陷密度、重开率、测试通过率、平均修复时长写成指标字典条目，看板/矩阵/报告同源可复算。

### 1.3 本轮不做（详见 §10 范围与非目标）

岗位工作台与企业级看板、自助报表与拖拽分析、邮件与出站 Webhook、Wiki、甘特图、价值流看板、工时填报与产能、周报月报、开放 API 的其余接口、多租户 SCHEMA/DATABASE 两种形态与迁移工具、二级企业的「我也需要」跟单、移动端、SSO/LDAP、自建 CI 执行器——均顺延到 M6–M9。

## 2. 用户与角色

平台共 **10 类用户**（9 类业务角色 + 平台管理员）。一人可挂多角色，权限取并集；审批人由流程定义动态指定，不写死角色。

| 角色 | 归属 | 本轮核心职责 | 数据可见范围 |
| --- | --- | --- | --- |
| **业务部门** | 甲方业务线 | 提报业务需求、看本部门需求进度与人天 | 本部门提报及相关 |
| **二级企业业务人员** | 二级管理企业 | 提报需求、只读浏览集团已入池业务需求**摘要**、看自己提报的缺陷摘要 | 自己提报的 + 已入池业务需求摘要 |
| **二级企业负责人** | 二级管理企业 | 审批本企业提报、看本企业全部提报 | 本企业全部提报 |
| **产品** | 甲方产品线 | 评审入池、拆解、版本编排、验收 | 所负责域/产品线 |
| **项目 / 域负责人** | 甲方 PMO | 排期、分派厂商、跨厂商协调、本域全量 | 所辖域全量 |
| **研发** | 厂商团队 | 承接研发需求、拆任务、填人天、填 MR、提发布 | 本厂商 + 被授权域 |
| **测试** | 厂商/甲方测试 | 维护用例与测试计划、执行、提缺陷、维护自动化登记 | 本厂商 + 被授权域 |
| **运维** | 甲方/厂商运维 | 发布执行、上线单、环境与窗口 | 所辖域 + 发布相关单据 |
| **管理层** | 甲方高层/PMO | 全局效能查看（默认只读）、流程定义与指标管理 | 全量（只读） |
| **平台管理员** | 平台方 | 租户/组织/厂商/域/账号/角色、流程定义、API 客户端、指标字典、审计查看 | 系统级（业务明细默认只看统计） |

补充：**域负责人**是「项目」角色的维度，7 个域各配负责人，域内可见本域全部厂商；**厂商负责人**是研发/测试中的管理岗，可指派本厂商人员，不可跨厂商。归属冲突时以 §7 的判定规则为准，不以角色名判断。

## 3. 业务流程与状态机

### 3.1 端到端主流程（本轮全链路）

```
二级企业/业务部门
   │ 提报 BUS-xxxx（审批：本企业负责人 → 集团产品经理，可配）
   ▼
待评审 ──评审──► 已入池 ──拆解──► 产品需求 PDR-xxxx ──拆解──► 研发需求 RD-xxxx
   │                                                              │
   │ 驳回 → 已提报（改后重提，新审批实例）                          ├─ 分派/转派厂商（留痕）
   ▼                                                              ├─ 拆任务 Task → 迭代 Sprint
版本计划 Release（规划中→已锁定→已发布）                            ├─ 填 MR / 预估·实际人天
   │                                                              ├─ 快速测试记录 / 测试计划执行
   │                                                              ├─ 缺陷 BUG-xxxx（新建→处理中→待验证→关闭，可重开）
   ▼                                                              ▼
发布上线单 DeployOrder ── 5 项准入校验(PASS/FAIL) ── 发布审批 ── 执行结果（成功/失败/回滚）
```

### 3.2 三类需求状态机（非法流转一律拒绝）

| 类型 | 编号 | 状态流转 |
| --- | --- | --- |
| 业务需求 | BUS-0001 | 已提报 → 审批中 → 待评审 → 已入池 →（关闭 / 驳回回「已提报」） |
| 产品需求 | PDR-0001 | 待分析 → 已排期 → 开发中 → 已交付 → 验收关闭 |
| 研发需求 | RD-0001 | 待开发 → 开发中 → 待测试 → 测试通过 → 已合入 → 完成 |

- 三层父子：业务需求 → 产品需求 → 研发需求；子必须挂父，父可挂多子，可跨 Release。
- 父需求详情展示子清单、完成率（按计数）、人天汇总、交付状态；**父需求人天只读**。
- 状态唯一入口 = 显式流转动作或审批结果回调；任何接口不得直接写 `status` 字段。
- 每次流转写 `audit_log`（from/to/操作人/时间/来源/备注）。

### 3.3 审批与状态机联动

| 单据 | 触发 | 通过 | 驳回 |
| --- | --- | --- | --- |
| 需求提报 | 提交提报 | 进「待评审」 | 回「已提报」，可改后重提（保留历史） |
| 评审入池 | 产品经理发起评审 | 进「已入池」 | 退「待评审」 |
| 需求版本 | 版本发布申请 | 版本「已发布」，级联推进关联需求 | 退「已排期」，需重新编辑 |
| 需求发布 | 研发/厂商提交发布单 | 单据「已批准」，可登记执行结果 | 回「待测试/开发中」，按节点回退 |

### 3.4 缺陷状态机与重开计数

```
新建 ──开始处理──► 处理中 ──提交验证──► 待验证 ──验证通过──► 关闭
                    ▲                    │                     │
                    └──验证驳回（重开+1）─┘                     │
                    └──────────────关闭后重开（重开+1）──────────┘
```

- 每次流转写 `defect_history`（from/to/操作人/意见/时间）并回写需求时间线。
- `reopen_count` 只在「待验证→处理中（驳回）」与「关闭→处理中（重开）」两处 +1。
- 关闭时写 `closed_at`；平均修复时长 = avg(`closed_at` − `found_at`)，只统计已关闭缺陷。

### 3.5 用例版本 → 计划 → 执行 → 缺陷 的关系

```
test_module(≤3 层) ── 1:N ── test_case(TC-xxxx) ── 1:N ── test_case_version(v1..vN 快照)
                                     │                            │
                                     │ 被引用（记录 case_version）  │
                                     ▼                            ▼
                          test_plan(挂 Release) ── test_plan_case ── test_execution(手工/自动)
                                                                        │ 失败
                                                                        ▼
                                                              defect（带 case_id/case_version/
                                                                      requirement_id/execution_id）
```

- 执行记录**必须**带 `case_version`；详情展示当时快照，而不是最新用例内容。
- 研发需求「测试通过」在门禁开启时只认计划执行结果（§4.14），不认人工点按。

### 3.6 追溯链与矩阵

```
需求(任一类) → 任务 → MR 链接 → 测试记录/执行 → 缺陷 → 发布单/版本
```

任一侧可反查；矩阵按需求维度实时计算缺口（不落快照，避免"矩阵绿了但链路断了"）。

### 3.7 关键页面与交互摘要

- **列表页**（需求池/缺陷/用例/任务/发布单/版本）：左侧筛选栏 + 右侧表格 + 顶部统计条；行点开右侧抽屉或详情页；批量操作仅允许权限内动作。
- **需求详情页**：概览 / 子需求 / 任务 / 测试 / 缺陷 / 审批 / 追溯 7 个 Tab；状态动作按钮由状态机与权限共同决定。
- **审批中心**：我的待办 / 已办 / 我发起；详情右侧为单据摘要（权限不足时仅摘要），左侧为流转时间线。
- **用例执行页**：左用例树，右执行表格（结果下拉 + 备注 + 附件），底部计划通过率/覆盖率实时汇总。
- **追溯矩阵**：需求行 × 6 列环节，缺口列可筛选并直接跳到缺失环节的创建页。
- 视觉与骨架统一按 `docs/teamflow/20261108-r2-devops-platform/UI-STYLE.md`（蓝鲸式左栏 + 顶部导航 + 白卡片 + 浅灰底 + 1px 细边框 + 浅底 pill 状态）。

## 4. 功能需求

### 4.1 租户、组织、厂商、业务域与账号

- **租户**：`tenant`（编码、名称、隔离形态、状态）。本期只实现 `ROW`（同库行级）；`SCHEMA`/`DATABASE` 留到 M9，字段与路由接口预留。
- **开通**：新建租户自动执行 Flyway 初始化 + 预置 10 个角色、7 个业务域、字典项；同一编码/手机号可跨租户重复。
- **组织树**：集团 → 二级管理企业 → 部门 → 人员；支持按企业批量建号、指定企业负责人。
- **厂商**：名称、编码、联系人、状态；厂商下挂人员。
- **业务域**：7 个域（编码、名称、负责人、启用状态），可增删。
- **用户**：组织 + 所属厂商（厂商人员）+ 被授权域集合；启用/停用/重置密码。
- **认证**：本地账号 + JWT；网关校验 token，服务内解析 `userId/tenantId/roles/domains/vendorId`。
- **租户上下文**：所有业务表带 `tenant_id`；请求头 `X-Tenant-Id` 必须存在且与 JWT 内 `tenantId` 一致，否则 403 且不落库；异步/内部调用显式传参，禁止依赖 ThreadLocal 隐式传递。
- **角色与权限**：角色绑定功能权限，数据范围由 §7 统一裁决，不由各页面各写一套。

### 4.2 需求提报

- 表单：类型（业务/产品/研发）、标题、描述、所属业务域、优先级（P0–P3）、期望交付时间、附件、提报单位（自动带出组织）、关联域（业务需求可多选）。
- 编号：按类型全局自增 + 前缀（BUS/PDR/RD-0001），按租户独立；不按年份/域分段。
- 提报后进入审批流（默认两级：本企业负责人 → 集团产品经理；集团内部：直属主管 → 产品经理），审批中可撤回。
- 驳回后回提报人，可修改重提；重提生成新审批实例，历史保留。
- 相似需求提示、「我也需要」跟单属 M8，本轮不做。

### 4.3 需求池

- 类型 Tab（业务/产品/研发）；筛选：父需求、版本、负责人、优先级、状态、业务域、厂商、提报企业、时间范围。
- 两种视图：**父需求聚合视图**（默认，展示子需求完成率与人天汇总）与**平铺视图**（逐条）。
- 业务方可见范围按 §7：二级企业用户只读浏览已入池业务需求的摘要（标题、摘要、所属域、状态、预计版本），**不含人天/成本/内部备注/研发细节**。
- 导出 CSV（本轮导出格式为 CSV，首行写水印元信息：导出人/时间/筛选条件），行数必须等于页面行数且只含权限内数据。

### 4.4 需求评审与入池

- 产品经理对「待评审」发起评审 → 选流程 → 提交 → 审批；通过进池，驳回退「待评审」。
- 评审记录：意见、驳回原因、关联需求；入池后可被版本引用与拆解。

### 4.5 需求拆解

- 业务需求「拆解」→ 新建产品需求（父=业务需求）；产品需求「拆解」→ 新建研发需求（父=产品需求）。
- 继承业务域，可覆盖优先级/交付期望；校验父子类型合法、禁止环、禁止跨类型跳级。
- 父需求完成率 = 子需求完成数 / 子需求总数；人天汇总 = 子需求之和（0.5 天精度，只读）。

### 4.6 版本计划

- Release：编码、名称、所属域、计划发布日、状态（规划中/已锁定/已发布/已取消）、里程碑列表。
- 版本可挂三类需求（业务需求按产品需求聚合展示），列表勾选加入；发布需走版本审批。
- 版本详情：需求清单、完成情况、人天预估/实际、风险需求（`plan_end_date` 已过且未完成 → 标红）。
- 版本「已发布」后其内容锁定（不可增删需求），再改必须新建版本。

### 4.7 研发交付

- 厂商研发认领/被分派研发需求 → 「开发中」；手工填 MR 链接（本期不对接代码平台）。
- **人天**：填预估/实际人天（0.5 天精度）+ 负责人；产品/业务需求由子需求汇总（只读）。手册与工时口径冲突时以工时为准的逻辑在 M8 上线，本轮实际人天为手填并记修正人。
- **快速测试记录**：测试人员可对研发需求登记一次「通过/不通过」（写 `test_execution`，`source=MANUAL`，`plan_id/case_id` 为空，`case_version` 为空）；通过后 RD 进「测试通过」。
- 提交发布申请 → 生成发布单（§4.9）。

### 4.8 自定义审批流

**引擎**：自研轻量审批引擎（不引入 Flowable/Camunda——Boot 4.0.9 + JDK 25 的第三方兼容性风险，且场景是固定单据的线性/条件流）。

- **流程定义**：按单据类型（需求提报/评审入池/需求版本/需求发布）建流程，可叠加「需求类型（业务/产品/研发）× 业务域」绑定；每类单据可设一个默认流程。
- **节点**：开始 → 审批节点（会签/或签）／条件分支（按需求类型、业务域、优先级、预估人天路由）／抄送 → 结束。节点必须解析出至少一个审批人，否则流程定义不允许发布（防卡单）。
- **审批人来源**：指定人、角色（产品经理/域负责人/PMO）、发起人直属主管、厂商负责人；支持节点级多人。
- **加签/减签**：前加签（新增人先于本人处理）、后加签（本人处理完交给新增人，可多人）；节点负责人或管理员可减签（需填原因并通知被减签人）；加签/减签写 `wf_history`；会签节点加签后必须新成员全部处理完毕才流转；已处理的审批任务不可加签。
- **版本化**：流程发布即固化版本；修改生成新版本，在途实例按启动时版本执行，不得卡死/跳步/重复；已发布版本不可编辑。
- **配置器**：表单式节点列表（不做 BPMN 拖拽画布）。
- **审批中心**：我的待办/已办/我发起；详情含流转记录（谁、何时、意见）与被审单据摘要（权限不足时仅摘要、无附件下载）；操作：同意、驳回、加签、减签、转办、撤回、催办。
- **数据模型**：`wf_definition`（单据类型+需求类型+域+版本+定义 JSON+启用）、`wf_instance`（记录 `definition_version`）、`wf_task`（含 `origin=INITIAL/ADD_SIGN`、`add_sign_type=BEFORE/AFTER`、`parent_task_id`）、`wf_history`。
- **权限**：流程定义仅 PMO/管理员可编辑；审批人看被审单据受 §7 约束。

### 4.9 发布上线单与准入校验

- **发布单**：关联 Release、需求清单（自动带出）、目标环境（测试/准生产/生产）、计划窗口、制品版本号（手工，可空）、上线步骤、回滚方案、影响范围、负责人。
- **准入校验（提交时自动执行，逐项 PASS/FAIL 并给出失败原因与修复指引）**：
  1. 关联需求全部测试通过（RD 状态 ≥「测试通过」；启用门禁时须计划门禁通过）。
  2. 无未关闭 P0/P1 缺陷（`severity∈{P0,P1}` 且 `status≠关闭`）。
  3. 研发需求 MR 链接已填。
  4. 人天（预估/实际）已填且 >0。
  5. 需求级审批已通过（关联需求的评审入池与版本审批实例均为批准）。
- 任一 FAIL → 提交返回 409，列明失败项；**绕过前端直接调接口同样拒绝**（服务端唯一判定）。
- **强制放行**：仅 PMO/管理员，必须填原因（空原因 400），写审计并通知域负责人；放行记录随单展示。
- **审批**：走 §4.8（单据类型=需求发布，可配运维会签）。
- **执行记录**：实际开始/结束、结果（成功/失败/回滚）、耗时、执行人、备注；失败可关联缺陷并重新发起。
- **统计**：发布日历（按环境/版本）、发布成功率、平均发布耗时、失败原因分布；数字可由单据明细复算。

### 4.10 缺陷管理

- **缺陷单**：编号 `BUG-0001`（按租户自增）；字段=标题、描述与复现步骤、严重级（P0 致命/P1 严重/P2 一般/P3 轻微）、优先级、关联研发需求、关联版本、关联用例（`case_id`）、用例版本、执行记录、发现人、处理人、所属域与厂商（隔离字段）、预计修复时间、附件。
- **隔离字段来源**：缺陷的 `domain_id`/`vendor_id` 由关联研发需求派生，不接受前端覆盖；无关联需求的手工缺陷必须显式选择域与厂商。
- **来源**：
  - 测试执行「失败」一键生成（自动带用例编号、用例版本、研发需求、版本、执行记录，并回填 `test_execution_id`）；
  - 手工提报（测试/运维/研发），上述关联可空。
- **状态机**：新建 → 处理中 → 待验证 → 关闭；待验证驳回回处理中（`reopen_count+1`）；关闭后可重开（`reopen_count+1`）；非法流转 409。
- **归属**：处理人默认取关联需求 `assignee_vendor` 的研发负责人，可指派给该厂商内成员。
- **列表与看板**：按域/厂商/版本/严重级/状态/处理人筛选；看板 4 个数字=未关闭 P0/P1 数、缺陷密度、重开率、平均修复时长，均可点入明细并用同一筛选复算。
- **业务方摘要视图**：业务部门/二级企业只看到自己提报需求衍生的缺陷**摘要**——状态、严重级、预计修复时间；看不到描述、复现步骤、附件、处理人、内部备注与其他厂商缺陷。
- **隔离**：满足 §7，列表/详情/导出/看板/矩阵全走同一过滤。

### 4.11 任务与迭代

- **任务**：研发需求下拆任务（标题、负责人、预估小时、起止日、状态=待办/进行中/完成/阻塞、排序）；状态变更写审计；完成率回写研发需求进度。
- **迭代**：挂在某 Release 下的时间盒（名称、起止日、目标、容量人天、状态=规划中/进行中/已关闭）；需求与任务可挂迭代。
- **看板**：迭代看板（按状态列、按人泳道，拖动改状态后刷新一致）；个人任务清单。
- **关闭规则**：关闭迭代时存在未完成任务必须迁移到下一迭代或退回待办，未迁移拒绝关闭并提示原因。
- **本轮口径**：任务预估小时只作工作量参考，不计入需求实际人天（工时模块 M8 上线后再切换口径，届时以指标字典版本记录变更）。

### 4.12 需求追溯矩阵

- 需求详情页「追溯」Tab 展示完整链路：需求 → 任务 → MR 链接 → 测试记录/执行 → 缺陷 → 发布单/版本，每环可反查（缺陷可跳需求，需求可跳缺陷）。
- 矩阵页：每行一条需求，列为 6 个环节（任务/MR/测试/缺陷/发布/版本），**实时计算**齐备性（不落快照、可缓存 ≤30s 但必须带版本号失效）。
- 缺口筛选：缺 MR / 缺执行记录 / 有未关闭 P0/P1 / 未发布 / 未关联用例；缺口行不得显示为齐备。
- 权限：厂商只看自己承接需求的链路；跨域/跨厂商链路不出现。

### 4.13 测试用例库

- **模块树**：项目/域 → 模块（**≤3 层**，第 4 层创建被拒绝并提示）→ 用例；支持拖拽移动、批量导入（CSV/XLSX，模板校验，失败行逐行报错）、批量导出（CSV，带水印元信息）、复制、禁用。
- **用例字段**：编号 `TC-0001`（按租户自增）、标题、模块、关联需求（可选）、类型（功能/接口/性能/兼容）、优先级 P0–P3、前置条件、步骤（序号/操作/预期结果）、标签、是否自动化、脚本标识。
- **版本化**：每次保存生成新版本（v1、v2…），`test_case_version` 存快照；`current_version` 指向最新；历史版本只读可查。
- **执行绑定**：执行记录必须带 `case_version`；用例改版后历史执行记录仍显示当时的步骤与预期。
- **不使用「用例评审」审批**：本轮不启用第五类单据（预留开关，默认关闭）。
- **删除**：软删；被计划或执行引用过的用例不可物理删除。

### 4.14 测试计划与执行

- **计划**：挂 Release（必填）、名称、执行人、时间窗、状态（草稿/执行中/完成）；选择用例集合，落 `test_plan_case`（记录 `case_version` 快照）。
- **执行结果**：未执行/通过/失败/阻塞/跳过；执行记录含实际结果说明、附件（截图/日志）、执行人、执行时间。
- **汇总**：计划通过率 = 通过数 / 计划内用例总数；执行覆盖率 = 已执行数（非「未执行」）/ 计划内用例总数；计划完成 = 无「未执行」。
- **失败转缺陷**：一键生成缺陷，自动带出用例编号、用例版本、关联需求、版本与执行记录链接（缺陷详情可回跳执行记录）。
- **测试门禁（研发需求「测试通过」）**：
  - 开关按 **版本（Release）级**配置，默认**开启**；
  - 开启时（严格模式，默认）：关联计划的计划内用例必须**全部为「通过」**才允许 RD 进「测试通过」；存在 未执行/失败/阻塞/跳过 任一即拒绝，并列出未通过的用例编号与当前结果；
  - 宽松模式（版本级可选）：仅「失败」阻断，阻塞/跳过须在计划上填写原因；
  - 门禁判定在服务端唯一实现，界面按钮置灰与接口拒绝同源；绕过前端直接改状态返回 409；
  - 计划未关联任何用例时按"不满足门禁"处理（并提示先纳入用例），避免空计划放行。
- **一致性**：执行记录是唯一事实源；需求的「测试通过」时间线引用最近一次放行的执行记录。

### 4.15 自动化结果上报（开放 API · 本轮唯一开放接口）

- **客户端**：`api_client`（名称、AppKey、密钥哈希、scopes、IP 白名单、限流 QPS、状态）；仅平台管理员可建/停/轮换密钥。
- **接口**：`POST /openapi/v1/test-executions`；Header：`X-App-Key`、`X-Timestamp`（±5 分钟）、`X-Signature`（HMAC-SHA256，签名串=`method\npath\nappKey\ntimestamp\nbodySha256`）；Body：`run_id`、`case_id`、`case_version`（可选，缺省取当前版本）、`result`（PASS/FAIL/BLOCKED/SKIP）、`duration_ms`、`log_url`、`executed_at`、`plan_id`（可选）。
- **校验与拒收**：未带/错签名 → 401；IP 不在白名单、scope 不含 `test:report`、客户端停用 → 403；未知 `case_id` → 422 `TEST_CASE_NOT_FOUND`；显式提供且不存在的 `case_version` → 422 `CASE_VERSION_NOT_FOUND`；`result=NOT_RUN` 或非法枚举 → 400；以上一律**不落库**。
- **幂等**：唯一键 `(client_id, run_id, case_id)`；重复上报返回 200 且 `idempotent=true`，不新增记录、不改变计划结果。
- **合并**：同一计划用例的新旧结果按 `executed_at` 取最新一条作为计划结果，历史全保留；手工与自动结果并存，来源可区分。
- **隔离与限流**：上报按 `plan_id`/`case_id` 归属推导租户与域/厂商，不接受调用方指定；默认 100 QPS/客户端，超限 429；每次调用写 `api_call_log`（含结果码、耗时、来源 IP）。
- **失败隔离**：上报失败不得影响手工执行、其他接口与其他客户端（独立事务与超时）。

### 4.16 指标口径（本轮最小指标字典）

| 编码 | 指标 | 公式 | 切片 |
| --- | --- | --- | --- |
| DEFECT_DENSITY | 缺陷密度 | 缺陷数 / 需求数 | 域、厂商、版本、月 |
| REOPEN_RATE | 重开率 | `reopen_count>0` 的缺陷数 / 缺陷总数 | 域、厂商、月 |
| TEST_PASS_RATE | 测试通过率 | 通过数 / 计划内用例总数（另给「已执行通过率」= 通过数 / 已执行数） | 版本、计划、域、厂商 |
| MTTR | 平均修复时长 | avg(`closed_at` − `found_at`)，仅已关闭缺陷 | 域、厂商、严重级、月 |

- 每条指标含编码、名称、主题、公式、数据源表、口径说明、负责人、版本、生效日期。
- 看板/矩阵/发布统计上的数字可点开显示定义并可下钻明细；同一筛选下三处数字必须一致（同一聚合接口，禁止各写一套 SQL）。
- 口径变更必须新增版本记录（旧版本可查），不得原地改公式。

- **审计**：状态流转、审批动作（含加签/减签/转办/撤回）、权限与角色变更、准入强制放行、缺陷重开、用例改版、执行上报、API 客户端变更、导出操作全部落 `audit_log`（user/action/biz_type/biz_id/detail_json/ip/created_at），可按单据反查。

## 7. 数据隔离与可见性规则

**隔离维度**：业务域（domain）× 厂商（vendor），外加最外层租户（tenant）。本轮为同库行级过滤（统一拦截器注入），表结构预留切独立 schema/库。

判定规则（按优先级短路，服务端唯一实现）：

1. **管理层 / PMO / 平台管理员（系统类）**：全量；管理层默认只读（除非被配置为审批节点）。
2. **甲方业务角色**：PMO/域负责人=所辖域全量；产品=所负责域全量；业务部门=本部门提报及相关；二级企业业务人员=自己提报的 + 全集团已入池业务需求**摘要**；二级企业负责人=本企业全部提报。
3. **厂商角色（研发/测试/厂商负责人）**：行可见当且仅当 `row.domain_id ∈ user.authorized_domains` **且**（`row.owner_vendor_id = user.vendor_id` 或 `row.assignee_vendor_id = user.vendor_id` 或该行被共享给其厂商）。
4. **审批场景**：审批人看被审单据时若数据权限不含明细，只给摘要，不提供附件与明细下载。
5. **统一生效面（本轮必须全覆盖）**：需求、缺陷、任务、版本、发布单、审批、用例、测试计划、执行记录、看板聚合、追溯矩阵、导出、附件下载必须走同一套行级过滤；**禁止只在列表接口做过滤**；开放 API 只返回调用方可见范围。
6. **租户边界**：请求缺少 `X-Tenant-Id` 或与 JWT 不一致 → 403 且不落库；不允许「落到默认库」；平台管理员只见租户列表与聚合统计，不提供跨租户明细接口。
7. **字段级脱敏（与行级正交）**：业务方对缺陷/需求只给摘要字段；成本人天、内部备注、厂商评分默认仅管理层/PMO 可见；页面、接口、导出、看板四个出口复用同一套字段过滤，不得漏配。
8. **缺陷与测试数据的特别约定**：缺陷的 `domain_id/vendor_id` 由关联需求派生、不可前端覆盖；执行记录与计划按 `plan_id → release → domain` 与用例所属域推导归属；跨厂商的用例/计划互不可见，即使在同一 Release 下。

### US-1（P0）租户与组织底座

- **AC-1**：平台管理员创建租户 T2 → 自动完成库结构初始化并预置 10 角色/7 域/字典；用 T2 账号登录，列表与详情只含 T2 数据，`tenant_id` 与 JWT 一致；请求缺少 `X-Tenant-Id` 或与 JWT 中 `tenantId` 不一致时返回 403 且数据库无新增行；同一 `code`/`username` 可在不同租户重复使用；T2 的 7 个域、角色、字典项齐全可用。

### US-2（P0）三类需求与三层拆解

- **AC-2**：可分别创建 BUS/PDR/RD 三类需求，编号按类型自增；父子组合仅允许 BUS→PDR→RD，其余组合（含 PDR 挂 PDR、BUS 挂 RD）返回 400 并给出原因；祖先环被拒绝；父需求 `estimate_days`/`actual_days` 由子需求求和（0.5 天精度）且接口拒绝手填；子需求跨 Release 时父汇总仍正确。
- **AC-3**：三类需求按各自状态机流转；非法流转（如 RD 从「待测试」直接到「完成」、BUS 从「已提报」跳「已入池」）返回 409 并说明允许的目标状态；直接 `PATCH status` 字段被拒绝（唯一入口为流转动作/审批回调）；每次合法流转写 `audit_log`，含 from/to/操作人/来源/备注，详情页时间线与之一致。

### US-3（P0）域 × 厂商隔离与权限矩阵

- **AC-4**：厂商 A 账号在 8 个入口——需求列表、需求详情、全局搜索、导出 CSV、附件下载、缺陷看板、用例列表、追溯矩阵——均看不到厂商 B 承接的数据；越权直连 URL 或按 ID 取详情返回 403 并写审计；撤销某域授权后，下一次请求（≤1s）即不可见；跨厂商转派后 B 立即可见、A 不可见，转派记录可查；PMO/管理层可见全量。
- **AC-5**：按 §6 矩阵逐格验证 10 类角色的功能权限（允许=2xx，不允许=403，受限按配置）；一人多角色时取并集；前端按钮隐藏不作为唯一防线——直接调用受限接口必须被服务端拒绝并记审计。

### US-4（P0）自定义审批流

- **AC-6**：四类单据均可配置流程并启用；可叠加「需求类型 × 业务域」绑定不同流程，未匹配时走默认流程；流程发布即固化版本号，已发布版本编辑返回 409；节点解析不出审批人时流程定义不允许发布（返回 400 并指出节点）。
- **AC-7**：会签（全员通过才过）、或签（任一通过即过）、条件分支（按需求类型/域/优先级/预估人天路由，命中第一个匹配分支）、抄送（不阻塞流转，产生通知）四种语义均正确；驳回终止实例并回退单据状态。
- **AC-8**：发布 v2 后新建单据走 v2，v1 在途实例按 v1 完整走完（含会签与加签），不卡死、不跳步、不重复生成任务；实例记录 `definition_version`，审批历史可按版本查。
- **AC-9**：加签（前加签：新增人先处理，本人随后；后加签：本人处理后交给新增人，可多人）、减签（需填原因，否则 400；被减签人收到站内通知）、转办、撤回（仅未处理节点可撤）、催办均可用；全部动作写 `wf_history` 并可查；会签节点加签后必须新成员全部处理完毕才流转；已处理的审批任务加签返回 409。
- **AC-10**：审批结果驱动状态机——提报通过进「待评审」、驳回回「已提报」（可改后重提，旧实例保留）；评审通过进「已入池」、驳回退「待评审」；版本审批通过版本「已发布」并级联关联需求、驳回退「已排期」；发布单审批通过可登记执行结果、驳回退回对应节点。

### US-5（P0）需求池与版本计划

- **AC-11**：需求池类型 Tab 与 8 个筛选项组合生效；同一筛选下父需求聚合视图与平铺视图的计数/行数一致；导出 CSV 行数等于页面行数、仅含权限内数据、首行含水印元信息；版本可挂三类需求并按父需求聚合，审批通过后级联；`plan_end_date` 已过且未完成的需求在版本详情标红并可筛选。

### US-6（P0）发布上线单与准入校验

- **AC-12**：发布单必须关联 Release 并自动带出需求清单；提交时逐项展示 5 项准入 PASS/FAIL；任一 FAIL 返回 409 并列出失败项与修复指引；绕过前端直接 POST 提交同样被拒；PMO 强制放行必须填原因（空原因 400）、写审计并通知域负责人，放行记录随单展示；审批通过后可登记执行结果（成功/失败/回滚）与实际耗时；发布成功率/平均耗时可由单据明细复算。

### US-7（P0）缺陷闭环（对应上一轮 AC-24）

- **AC-13**：可创建 BUG 单（P0–P3），`domain_id/vendor_id` 由关联需求派生且前端不可覆盖；来源支持「测试执行失败一键生成」（自动带用例编号、用例版本、研发需求、版本、执行记录链接）与手工提报；状态机 新建→处理中→待验证→关闭，待验证驳回与关闭后重开均使 `reopen_count+1`，非法流转 409；缺陷列表/看板可按域/厂商/版本/严重级/状态/处理人筛选；看板 4 个数字（未关闭 P0/P1、缺陷密度、重开率、平均修复时长）与同筛选明细逐项复算一致；业务方只看到状态/严重级/预计修复时间三项摘要，看不到描述、复现步骤、附件、处理人；厂商 B 在列表/详情/导出/看板均看不到厂商 A 的缺陷。

### US-8（P0）任务与迭代

- **AC-14**：研发需求可拆任务（负责人/预估小时/起止日/状态），任务完成率回写需求进度且详情可见；迭代挂在 Release 下，需求与任务可加入；迭代看板拖动改状态后刷新一致且写审计；关闭迭代时存在未迁移任务则拒绝关闭并提示迁移去向；任务预估小时不计入需求 `actual_days`（口径写入指标字典说明）。

### US-9（P0）需求追溯矩阵（对应上一轮 AC-26）

- **AC-15**：任一类需求详情可看到 需求→任务→MR→执行记录→缺陷→发布单/版本 的完整链路，各环节可互跳；矩阵页 6 列齐备性由实时查询计算：`mr_url` 为空显示「缺 MR」、无执行记录显示「缺执行」、有未关闭 P0/P1 显示「阻塞」、无发布单显示「未发布」，任一缺口不得显示为齐备；缺口筛选可用；厂商只能看到自己承接需求的链路（跨厂商行不出现）。

### US-10（P0）测试用例库与测试执行（对应上一轮 AC-32）

- **AC-16**：模块树最多 3 层，第 4 层创建返回 400；用例编号 TC-xxxx；保存生成新版本，执行记录绑定 `case_version`，用例改版后历史执行详情仍展示当时步骤与预期；测试计划挂 Release 并纳入用例，执行结果为 通过/失败/阻塞/跳过/未执行；计划通过率=通过/计划内总数、覆盖率=已执行/计划内总数，页面数字与明细复算一致；执行失败一键转缺陷并自动带用例/版本/需求/执行记录；门禁开启（默认）时，计划内存在 未执行/失败/阻塞/跳过 任一即拒绝 RD 进「测试通过」并列出未通过用例，全部通过才放行；宽松模式下仅失败阻断且阻塞/跳过须填原因；计划无用例时按不满足门禁处理；绕过界面直接改状态同样 409。

### US-11（P0）自动化结果上报（对应上一轮 AC-33）

### US-14（P1）性能与稳定性

- **AC-20**：10 万条需求数据集下需求列表 P95 ≤1s、缺陷/测试看板 ≤2s、准入校验 ≤500ms、追溯矩阵（1 万需求）≤2s、执行上报 P95 ≤300ms（20 并发）、1000 条用例导入 ≤10s；压测脚本与结果记录随验收报告提交。

## 11. 反面目标（技术通过但会被退货的情形）

1. **用例改到第 3 版，历史执行记录却显示最新内容**：测试结论无法追责，QA 与研发各说各话——执行记录没有真正绑定 `case_version`，或详情页读的是用例主表。
2. **自动化上报把通过率刷高**：重复上报产生多条执行记录，或未知用例/错误版本被静默接收——报表上的通过率与真实执行对不上，管理层按此决策。
3. **门禁只在按钮上**：界面把「测试通过」置灰，直接调接口仍能过；或计划里还有「未执行/阻塞」也算通过——门禁形同虚设，发布准入跟着失真。
4. **缺陷看板一片绿但点不进去**：缺陷密度/重开率/平均修复时长与列表复算不一致；或业务方点开摘要，却看到跨厂商缺陷、描述与附件。
5. **追溯矩阵全勾而链路是断的**：MR 为空、无执行记录仍显示「齐备」；准入校验能显示 PASS/FAIL，但绕过前端就能提交发布单。

## 15. 假设与待澄清

> 下列 5 项是尚未定稿、需要你拍板的；其余设计取值已在正文以「默认」标注（如：JWT 本地账号、CSV 导出带首行水印、父需求人天只读、快速测试记录写 `test_execution`、演示规模 7 域/3 厂商/10 账号），若确认单另有指示则相应调整，不改变验收口径。

- **T1（口味）门禁严格度**：本轮默认「严格模式」——计划内用例必须全部为「通过」才放行「测试通过」，未执行/阻塞/跳过都阻断，并可按 Release 切换宽松模式（仅失败阻断）。理由：用户原话「全部执行且无失败」若把阻塞算作执行过，等于给了一条绕过门禁的捷径，与反面目标 3 直接冲突。若你更希望宽松（无失败即过），改默认即可；改动范围＝AC-16 的断言口径与门禁实现分支。
- **T2（口味）通过率分母**：默认 通过率 = 通过数 / 计划内用例总数（严格），另给「已执行通过率」作辅助列；覆盖率 = 已执行 / 计划内总数。若你希望通过率按已执行算，报表与看板数字会整体变好看但掩盖未执行；改动范围＝AC-16/AC-18。
- **T3（口味）缺陷口径**：默认 重开率 = `reopen_count>0` 的缺陷数 / 缺陷总数，且「待验证驳回」与「关闭后重开」都计次；缺陷密度 = 缺陷数 / 需求数（按域/厂商/版本/月切片）。若你希望驳回不算重开、或密度按千行代码/用例数算，指标字典与 AC-13/AC-18 的断言随之调整。
- **F1（事实）首批对接的 CI 系统未定**：仓库与需求都没有指定 Jenkins / GitLab CI / 自研流水线。默认只交付通用上报契约 + bash/curl 示例脚本，不做任何 CI 插件；拿到具体系统后需补一份对接示例（约 1 工作日），不影响 AC-17 验收。
- **F2（事实）M4 缺陷自动生成的过渡口径**：用例库与执行记录在 M5 才交付，M4 的「执行失败自动生成缺陷」缺少用例来源。默认 M4 先以研发需求的「快速测试记录」为源（写同一张 `test_execution`，`plan_id/case_id` 可空），M5 接通用例执行后同一入口自动带出用例/版本/执行记录，验收统一在 M5 后执行。若你要求 M4 当场就必须带用例与版本，则 M4/M5 需合并交付、工期约 +5 工作日。
